Normalized Grammar Specification ​

This document defines the normalized grammar for OmniUI v1. The goal is to make the language syntactically coherent by separating structural nodes, directives, explicit components, and native Markdown content.

1. Syntax Families ​

OmniUI uses the following syntax families to ensure every top-level syntactic marker belongs to a single family:

FamilyPrefix / FormPurpose
Structural nodes~Layout and block AST nodes (Layout Primitives)
Directives%Authoring / expansion directives (e.g., % DataGroup)
Explicit components[content](Target.tokens)Canonical inline UI components (e.g., [Save](Button))
MarkdownNative MarkdownContent (Paragraphs, Headings, Lists, etc.)
ShortcutsShorthand patternsAuthoring sugar only (e.g., [ ] for Checkbox)

2. The Canonical Rule ​

The OmniUI core grammar is fully expressible without shortcuts. Shortcuts are optional sugar and are not the canonical internal representation.

For example, a checkbox shortcut parses into its canonical component equivalent:

Shortcut FormCanonical Equivalent
[ ] Remember me[Remember me](Checkbox)
---~ Divider
(12)[12](Badge)

3. Mandatory Root Node ​

Every .ui document must start with exactly one root node:

OmniUI
Codeomniui
~ Ui
  ~ Stack
    [Inbox](NavItem.active)

WARNING

The ~ Screen directive is deprecated and not part of the normalized grammar. Use ~ Ui instead.

4. Structural Nodes (~) ​

Structural nodes define the block-level structure (the "skeleton") of your UI.

  • ~ Ui: Mandatory document root.
  • ~ Stack: One-dimensional layout (Vertical/Horizontal).
  • ~ Grid: Two-dimensional layout.
  • ~ Card: Semantic container with padding and border defaults.
  • ~ Divider: Visual separator.
  • ~ DataGrid: Semantic wrapper for Markdown tables.
  • ~ Overlay: Floating elements (Tooltips, Popovers, Modals, Bottom Sheets).
  • ~ Spacer: Flexible space consumer inside Stacks.

5. Explicit Components ​

Components are the interactive elements or semantic content blocks. They always follow the link-style syntax:

OmniUI
Codeomniui
[Label](Component.tokens@id)
  • Label: Markdown content inside [].
  • Component: The identifier (e.g., Button, Input).
  • Tokens: Dot-separated modifiers (e.g., .primary, .fill).
  • @id: Optional anchor for overlay targeting.

Write Less, Describe More ​

OmniUI is built for humans first, and for LLMs too.

The goal is simple: write as little as possible while describing as much as possible.

To keep authoring ergonomic, OmniUI supports equivalent ways to express attributes:

  • Inline attributes when the component is simple.
  • Property blocks when the component grows and readability matters more.

Both forms are valid. Pick the one that is easiest to scan and maintain.

A practical rule of thumb ​

  • Put style/variant tokens in the component target (.ghost.sm, .email.fill).
  • Put behavior/configuration attributes as attributes (disabled, value=..., showLabel), either inline or in a property block.

Equivalent syntax examples ​

These are equivalent:

OmniUI
Codeomniui
[[chevron-up](Icon) Move up](Button.ghost.sm disabled)
OmniUI
Codeomniui
[[chevron-up](Icon) Move up](Button.ghost.sm)
  - disabled

For more complex fields, property blocks are usually easier to read:

OmniUI
Codeomniui
[Support email](Input.email.fill)
  - showLabel
  - disabled
  - value="disabled@example.com"

Equivalent inline form:

OmniUI
Codeomniui
[Support email](Input.email.fill showLabel disabled value="disabled@example.com")

6. Parsing Priority ​

OmniUI resolve overlaps using a deterministic priority:

  1. Literal Escape (!!): Disables all shortcut processing for that line.
  2. Shortcuts: [ ], ( ), ---, etc.
  3. Explicit Components: [Label](Component).
  4. Native Markdown: Headings, Lists, Tables.
  5. Structural Nodes: ~ Node.
  6. Directives: % Directive.

7. Normalization Rules ​

  1. ~ always introduces a structural node.
  2. % always introduces a directive.
  3. [content](Target...) always introduces a component or include.
  4. Markdown remains content and is preserved as such.
  5. Shortcuts are sugar only; they must be expandable to canonical syntax.
  6. Aliases like ~ row or ~ col are forbidden in favor of ~ Stack horizontal.
