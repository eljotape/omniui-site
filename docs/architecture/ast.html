OmniUI AST Specification (MVP v1) ​

This document defines the Abstract Syntax Tree (AST) used by OmniUI.
The AST is designed to support:

  • Rendering wireframes (SVG / Preview)
  • Generating Figma structures
  • Adapting to Design Systems (Fluent, Material, etc.)

The model intentionally stays small and stable (11 nodes) so the parser and renderers remain simple.

Authoring-layer note:

  • directives such as % DataGroup ... are intentionally outside this AST
  • they are expected to expand before AST emission
  • they are implemented in parser expansion and do not persist as AST nodes

Node Overview ​

All nodes share these base properties:

id: string
type: string
loc: {
startLine: number
startCol: number
endLine: number
endCol: number
}
children?: Node[]

The loc property enables:

  • editor highlighting
  • preview ↔ editor synchronization
  • outline navigation

Component content note:

  • component nodes keep the raw label string and parsed inline markdown segments
  • this preserves formatting inside [content](Component.tokens) for bold, italic, strikethrough, highlight, inline code, links, images, emoji, and explicit line breaks

1. Document ​

Root node representing a single screen.

Document { meta?: { layout?: string canvas?: string } regions: Region[] }

Example metadata (optional):

~ Layout: header-aside-main-footer
~ Canvas: desktop-1440x1024

2. Region ​

Declared using:

~ Header
~ Main
~ Aside
~ Footer
~ Left
~ Right

Case-insensitive.

Region { name: string body: Block[] }

3. SemanticBlock ​

Optional semantic modes inside a region.

~ Form
~ Navigation
~ States

SemanticBlock { kind: "Form" | "Navigation" | "States" body: Block[] }

Notes:

  • Navigation can also be inferred heuristically when lists appear inside Aside.
  • Explicit declaration overrides heuristics.

4. MarkdownBlock ​

Represents regular Markdown content.

MarkdownBlock { markdown: string }

Examples:

  • paragraphs
  • lists
  • headings
  • strikethrough and highlight spans
  • inline code and fenced code blocks
  • images
  • standard markdown tables (data tables)

5. LayoutTable ​

Markdown tables interpreted as layout containers rather than data tables.

Rules:

  • Tables inside regions are candidates for layout tables.
  • Header rows with only empty cells are ignored.
  • Separator rows define alignment when present.
  • Alignment is inferred when missing.

LayoutTable { columns: ColumnSpec[] rows: TableRow[] }

6. ColumnSpec ​

Defines alignment for each column.

ColumnSpec { align: "left" | "center" | "right" }

Alignment rules:

If explicit separators exist:

|:--|:--😐--😐

Use them.

If not:

2 columns → left / right
3 columns → left / center / right
4+ columns → all left except last right

7. TableRow ​

TableRow { cells: TableCell[] }

Rows with no content are ignored by the renderer but still parsed.

8. TableCell ​

Cells may contain UI elements or markdown.

TableCell { align?: "left" | "center" | "right" body: Block[] }

Content inside a cell flows horizontally by default.

Notes:

  • column alignment may come from the separator row
  • a cell may override that with inline alignment shortcuts such as : value : or value :

9. Button ​

Generated from syntax:

[Label]

Button { label: string variant: "primary" | "secondary" | "danger" | "ghost" size: "sm" | "md" | "lg" flags: { disabled?: boolean loading?: boolean full?: boolean } icon?: IconToken[] }

Example:

[Sign in]
[Delete]

10. Field ​

Unified representation for inputs, selects, checkboxes, radios, etc.

Example syntax:

  • Email *

Field { label: string required?: boolean disabled?: boolean sizing?: "hug" | "fill" icon?: IconToken control: Control }

Control variants:

Control = | { kind: "input" inputType: "text" | "email" | "password" | "search" | "number" size: "sm" | "md" | "lg" placeholder?: string } | { kind: "textarea" size: "sm" | "md" | "lg" placeholder?: string } | { kind: "select" size: "sm" | "md" | "lg" mode?: "dropdown" | "list" value?: string options?: string[] } | { kind: "checkbox" checked?: boolean } | { kind: "radio" selected?: boolean group?: string } | { kind: "toggle" on?: boolean }

Authoring note:

  • markdown checkbox rows like [x] Checked option normalize to checkbox controls in the parsed model
  • parenthesized rows like (x) Checked option and (o) Selected option normalize to checkbox/radio controls in the parsed model
  • ( ) inherits its control type from the contiguous block: checkbox when the block contains any (x), otherwise radio
  • !! bypasses heuristic expansion and produces plain TextNode content

11. IconToken ​

Represents icon usage in UI elements.

IconToken { source: "emoji" | "ds" value: string }

12. Logo ​

Generated from syntax:

[Brand]

Logo { text: string size: "sm" | "md" | "lg" }

Examples:

mail as IconComponent
lock as IconComponent
home as IconComponent

Adapters may map emojis to design system icons.

Block Union Type ​

Blocks used inside regions and cells.

Block = | MarkdownBlock | SemanticBlock | LayoutTable | Button | Field

Example AST ​

Input:

txt
~ Header
| | | |
|---|---|---|
| list-icon Gmail | search action button | settings-icon user-icon |

AST:

Document └ Region(Header) └ LayoutTable └ Row ├ Cell(left) │ └ MarkdownBlock("list-icon Gmail") ├ Cell(center) │ └ Field(kind=input, type=search) └ Cell(right) └ MarkdownBlock("settings-icon user-icon")

Design Goals ​

The AST is intentionally minimal to ensure:

  • deterministic parsing
  • simple rendering to SVG
  • easy mapping to Figma
  • adapter compatibility with multiple design systems

Future extensions should add new nodes without breaking existing ones.
