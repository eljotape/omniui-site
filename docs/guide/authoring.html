Authoring-First UI Description ​

OmniUI (OUi) is designed for two audiences: those describing UI quickly (Authoring audience) and those needing exact, low-level control (Precision audience).

1. The Dual-Layer Strategy ​

OUi is syntactically coherent when treated as two interactive layers:

The Shortcut Layer (Authoring Sugar) ​

Designed for speed and human readability. Use this when you are mocking or wireframing rapidly.

Example:

OmniUI
Codeomniui
[ ] Remember me
[x] Accept terms
( ) Weekly digest
(o) Monthly digest
---

The Core Grammar (Precision Source) ​

The "canonical" form of the language. Use this for exact control over attributes, IDs, and complex nesting.

Example:

OmniUI
Codeomniui
[Remember me](Checkbox)
[Accept terms](Checkbox selected)
[Weekly digest](Radio)
[Monthly digest](Radio selected)
~ Divider

2. Structural Patterns ​

Mandatory Root ​

Every document starts with ~ Ui. Under it, you use ~ Stack and ~ Grid to build the layout.

OmniUI
Codeomniui
~ Ui
  ~ Stack border padding=24 gap=12
    ## Section Title
    [Action](Button.primary)

Alignment Model ​

Alignment is explicit in the normalized grammar. Use alignH for horizontal and alignV for vertical axes.

  • alignH=start | center | end | between
  • alignV=start | center | end | stretch

Example:

OmniUI
Codeomniui
~ Stack horizontal alignH=end gap=sm
  [Cancel](Button.secondary)
  [Submit](Button.primary)

3. Inline vs block Components ​

Explicit Components ​

Components are the primary interactive units: Button, Input, Select, Checkbox, Toggle, Badge.

They follow the link syntax: [Label](Component.tokens).

Markdown Integration ​

Native Markdown content remains valid inside OmniUI documents. Headings (#, ##, ###), Lists (-, +, *), and Tables all render as semantic content blocks within the UI structure.

For table-like UI, treat DataGrid as the default authoring surface. Markdown table rows are normalized as implicit DataGrid blocks, backed by internal Table/TableRow/TableCell structures in parser/runtime.

4. Authoring Directives (%) ​

Directives like % DataGroup help expand the UI without adding permanent AST nodes. They are authoring tools that "vanish" during final rendering.

Example:

OmniUI
Codeomniui
% DataGroup repeat=3
  ~ Card padding=12
    ### Activity row
    Static content repeated exactly.

% DataGroup repeat=3 fake
  ~ Card padding=12
    ### Activity row
    Generic fallback fake content.

% DataGroup repeat=3 fake=[avatarName,messageHeader,message]
  ~ Card padding=12
    ### Activity row
    Recent message text here...

DataGroup details are documented at /language/datagroup, including:

  • repeat-vs-fake rules
  • leaf replacement scope (Text nodes and component labels)
  • cyclic hint application order
  • implemented fake hint catalog and fallback behavior
  • parser warning semantics

5. Summary Policy ​

  1. Inference-first defaults: OUi aims to infer common intent.
  2. Explicit override safety: Every inferred behavior can be overridden with explicit attributes.
  3. Predictable fallback: If something is ambiguous, use the explicit canonical form.
